# MS Audio 운영 체계와 Phase 1 진행 설계

작성일: 2026-11-26
상태: 초안 (대표 승인 대기)
관련: 제품 설계 `docs/superpowers/specs/2026-11-24-choir-mr-mvp-design.md` (이하 '제품 설계')

## 1. 왜 만드는가

- 대표(사용자)는 혼자 개발한다. 모든 일을 직접 챙길 수 없으므로, **역할별 에이전트가 스스로 일하고 결과와 피드백을 대표에게 먼저 보고하는 체계**가 필요하다. (대표 발언: "내가 모든 것을 컨트롤 할 수 없기 때문에 계속 나한테 피드백과 결과를 스스로 제공할 수 있는 시스템")
- 회사 이름은 **MS Audio (가칭)**. 조직은 "가장 효율적인 개발을 위한 생각"이며 깊게 형식화할 필요는 없다 (대표 발언).
- 대표가 정한 회사 목표:
  1. 디자인하고 기능을 넣어 웹툴(MVP) 출시
  2. 기능 개선을 위한 지속적인 연구
  3. 셀프 피드백 (대표의 방향성에 대한)

## 2. 목표 / 비목표 / 반목표

### 목표
- O1. 대표가 세션을 열면 **무엇이 끝났고, 무엇을 정해야 하는지** 1분 안에 알 수 있다.
- O2. 각 역할이 정해진 형식으로 결과를 남겨, 다른 PC·다른 세션에서도 이어서 일할 수 있다 (기존 STATE.md 방식 유지).
- O3. 대표가 세션을 열도록 **알림**이 간다 (대표 요청).
- O4. 이 체계 위에서 Phase 1(웹 MVP)을 제품 설계 §7의 기간(최대 2주) 안에 출시한다.

### 비목표
- 사람 회사 흉내(직급, 회의록, 결재선). 역할은 일을 나누는 도구일 뿐이다.
- 대표 없이 클라우드에서 혼자 개발·배포하는 완전 자동화 (접근법 B, §4). 웹이 배포된 뒤 다시 검토한다.
- 마케팅팀은 지금 만들지 않는다. Phase 2(제품 설계 §7) 시작 때 만든다. (내 판단: 지금은 팔 것이 없다)

### 반목표 (돌아가도 이렇게 되면 실패)
- X1. **조직 꾸미기가 출시를 미루는 것.** 이 문서가 다루는 체계 구축은 하루 안에 끝낸다. 대표의 과거 실패 원인(완벽주의, 재미있는 것만 하기, 흥미 상실)이 '조직 만들기'로 재현되면 안 된다.
- X2. 보고서가 길어서 아무도 안 읽는 것. 대표 보고서의 첫 화면(요약 + 결정 필요)은 10줄 이내.
- X3. 감사(셀프 피드백)가 듣기 좋은 말만 하는 것. 감사는 목표에서 벗어난 점을 반드시 구체적으로 지적한다.
- X4. 연구소가 웹 출시 일정을 잡아먹는 것. 연구는 기간을 정해 두고, 엔진 반영은 대표 청취 승인 후에만 한다.

## 3. 제약

- 기존 작업 방식 유지: superpowers 설계 → 계획 → 에이전트 개발, `CLAUDE.md` + `docs/STATE.md` + `todo.md`로 여러 PC에서 이어서 작업, 한국어 커밋 메시지.
- 예산 최소 (제품 설계 §4). 정기 자동 실행은 알림 정도의 가벼운 것만.
- GPU(RTX 3060)와 시험 음원(`Test AR/`, git 제외)은 로컬 PC에만 있다. 클라우드 에이전트는 엔진 실행·청취 자료 생성을 못 한다.
- 원격 저장소: `github.com/MS-Won/AI_Stem`. 알림이 최신 상태를 읽으려면 세션 끝에 push가 되어 있어야 한다.

## 4. 접근법

| | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A (선택)** | 역할별 에이전트(`.claude/agents/`) + 대표 보고서 형식. 메인 세션이 '기획실'로 일을 나누고 보고 | 지금 방식에 얹기만 하면 됨, 비용 없음 | 대표가 세션을 열어야 진행됨 → 알림으로 보완 |
| B | A + 클라우드 정기 실행으로 스스로 점검·보고 | 세션 없이도 보고 | 비용, 클라우드에 GPU·음원 없음 → 연구·엔진 불가 |
| C | 에이전트 없이 보고 형식만 | 가장 가벼움 | '스스로 피드백하는 체계'가 안 됨 |

- **대표 결정: A.** "내가 세션을 열 수 있게 계속 알림을 주면 된다." → 알림만 가볍게 자동화한다 (§7).

## 5. 조직

메인 세션(Claude)이 **기획실**을 맡고, 나머지는 `.claude/agents/<이름>.md`로 정의한 에이전트다. 각 에이전트 정의에는 역할, 읽어야 할 문서, 산출물 형식, 하면 안 되는 것을 쓴다.

| 부서 | 에이전트 | 하는 일 | 산출물 | 하면 안 되는 것 |
|---|---|---|---|---|
| 기획실 | (메인 세션) | 대표 지시를 받아 일을 나누고 순서를 정함. 로드맵·STATE·todo 관리. 대표 보고서 작성 | 대표 보고서, 결정 로그, STATE.md | 대표 결정 사항을 혼자 정하기 |
| 디자인팀 | `design` | 브랜드 기초(MS Audio 로고 방향, 색, 글꼴), 화면 시안(랜딩·업로드·결과), 랜딩 문구 | `docs/company/design/` 시안, 대표 확인용 Artifact 페이지 | 시안 승인 전 실제 화면 구현 |
| 개발팀 | `developer` | 웹(`web/`, Next.js+Supabase), GPU 워커, 엔진 연결. 계획서의 작업 단위를 TDD로 구현 | 코드 + 테스트, 커밋 | 계획서 밖 기능 추가, 테스트 없이 커밋 |
| 연구소 | `research` | 엔진 개선 연구(첫 과제: 라이브 음원 끊김, 청취 판정과 맞는 지표 정의). 실험 스크립트·청취 자료 | `docs/company/research/<날짜>-<주제>.md` + 청취 파일 경로 | 대표 청취 승인 없이 엔진 코드 변경, 정해진 기간 초과 |
| 품질팀 | `qa` | 개발 결과 리뷰, 테스트 실행, 배포 URL에서 실제 사용 흐름 점검(브라우저) | QA 결과 (통과/문제 목록) | 직접 고치기 (문제는 개발팀으로) |
| 감사실 | `auditor` | 셀프 피드백. 방향이 목표(첫 1원, 출시 기간)에서 벗어났는지, 완벽주의·재미만 쫓기·범위 확장이 보이는지 점검 | 대표 보고서의 '감사 의견' 칸 | 코드·문서 수정 (읽기 전용) |

- 개발팀 에이전트는 superpowers의 subagent-driven-development가 부르는 구현 담당으로 쓴다. 에이전트 정의에는 프로젝트 함정(`CLAUDE.md`)과 스택 규칙을 담는다.
- 각 에이전트의 모델·도구 범위는 빌더가 정한다 (§9).

## 6. 일하는 흐름

1. 대표가 세션을 연다 → 기획실이 STATE.md와 최신 보고서를 읽고 "대기 중인 결정"부터 묻는다.
2. 대표 지시 → 기획실이 부서별 작업으로 나눈다. 새 기능은 기존대로 설계 → 계획 → 개발.
3. 부서 작업 → 개발이면 품질팀 리뷰를 거친다.
4. 큰 작업 단위(계획서 하나, 또는 하루 작업)가 끝나면 감사실이 점검한다.
5. 기획실이 **대표 보고서**를 쓰고, STATE.md·todo.md를 갱신하고, 커밋·push한다.

### 대표 보고서 형식
위치: `docs/company/reports/YYYY-MM-DD-<주제>.md`

```
# <날짜> <주제>
## 요약 (3줄 이내)
## 대표 결정 필요 (없으면 "없음")
- 질문 / 선택지 / 기획실 추천
## 한 일과 결과물 (경로·링크)
## 감사 의견
## 다음 할 일
```
- 첫 두 칸이 10줄을 넘지 않는다 (X2).
- 결정 사항은 `docs/company/decisions.md`에 한 줄씩 쌓는다 (날짜, 결정, 이유).
- STATE.md 맨 위에 최신 보고서 링크와 대기 중인 결정을 둔다.
- `docs/company/README.md`에 조직표(§5)와 이 흐름을 짧게 둔다. CLAUDE.md 문서 지도에도 추가한다.

## 7. 알림

- 세션 중: 오래 걸리는 작업(분리 실행, 긴 개발)이 끝나거나 대표 결정이 필요해지면 바로 알림을 보낸다 (Claude Code 푸시 알림).
- **알림 경로: 휴대폰 Claude 앱 푸시 (대표 결정).** 세션 중 알림과 세션 밖 알림을 같은 곳에서 받는다.
- 세션 밖 (내 판단): **평일 아침 1회** 클라우드 예약 작업이 GitHub의 STATE.md와 최신 보고서를 읽고 "결정 대기 N건 / 오늘 할 일 1~3개"를 푸시로 알린다. 저장소에는 아무것도 쓰지 않는다. 비공개 저장소라면 예약 작업에 GitHub 읽기 권한을 연결한다.
  - 대기 중인 결정도 할 일도 없으면 알리지 않는다 (알림 피로 방지).
  - 비용을 아끼려고 가벼운 모델을 쓴다.

## 8. Phase 1 진행 순서 (제품 설계 §6·§7, 최대 2주)

각 단계는 기존대로 자체 계획서(필요하면 설계)를 갖는다. 이 문서는 순서와 담당만 정한다.

0. 기획실: Phase 0 브랜치(`phase0-engine`)를 main에 합친다. 운영 체계(§5~§7) 구축 — 하루 안 (X1).
1. 디자인팀: 브랜드 기초 + 화면 시안 3개(랜딩 A/B 플레이어, 업로드·처리 중, 결과) → **대표 승인**.
2. 개발팀 (1과 병행 가능): `web/` 뼈대, Supabase 스키마(`profiles`, `jobs`, `credit_ledger`), 소셜 로그인, RLS(anon 검증), 업로드.
3. 개발팀: GPU 워커와 작업 흐름 (업로드 → 처리 → 결과 저장 → 상태 갱신), 24시간 자동 삭제.
   - **워커는 대표 PC(RTX 3060)에서 돈다 (대표 결정, 비용 0원).** 워커가 Supabase `jobs`에서 대기 작업을 가져와 한 번에 한 곡씩 처리한다. PC가 꺼져 있으면 작업은 대기 상태로 남고, 화면에 "처리 대기 중"과 예상 시간을 보여 준다. 사용자가 늘면 서버리스 GPU로 옮긴다 (그때 다시 결정).
   - 공개 출시 전 라이선스 미확인 모델(`MODELS.md`의 BS-RoFormer)을 확인하거나 대체한다 (내 판단: 출시 조건).
4. 개발팀: 승인된 시안으로 화면 구현 (결과 화면 A/B, 구간 표시, 다운로드, 무료 2곡 한도).
5. 품질팀: 배포 URL에서 실제 곡 1개(스튜디오 곡 `낡은 침대를 타고`)를 처음부터 끝까지 처리 → 통과하면 Phase 1 완료 (제품 설계 §7).
- 라이브 음원 (내 판단): 업로드는 받되 "라이브 음원은 일부 구간이 끊겨 들릴 수 있다"는 안내를 업로드·결과 화면에 띄운다. 랜딩 예시는 스튜디오 곡으로 만든다.
- 기간 (내 판단): 2주는 `phase0-engine`을 main에 합친 날부터 센다. 넘기면 감사실이 지적하고, 범위를 줄일지 대표가 정한다.
- 연구소: 위와 병행하되 웹 일정에 영향이 없게, 대표가 연구를 지시할 때만 진행 (X4).
- 감사실: 각 단계가 끝날 때마다, 그리고 1주가 지났을 때 점검.
