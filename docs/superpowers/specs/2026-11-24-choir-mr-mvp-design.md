# 합창·뮤지컬 MR 웹툴 MVP 설계

작성일: 2026-11-24
상태: 초안 (사용자 승인 대기)

## 1. 한 줄 요약

**"합창 구간에서도 반주가 원곡처럼 꽉 차게 들리는 MR"** 을 만들어 주는 웹툴.
뮤지컬·합창·성가곡처럼 MR을 구하기 어려운 곡을 쓰는 사람들에게 판다.

## 2. 왜 만드는가

- 사용자(개발자 본인)는 Gaudio Studio 등 MR 툴을 많이 써 본 뮤지컬 동호회 회원이다.
  가요가 아닌 곡은 공식 MR을 구하기가 매우 어렵다.
- 기존 툴을 쓰며 겪은 문제 (사용자가 직접 말한 것):
  1. Vocal Cut과 Stem으로 만든 MR 결과가 항상 달라서 둘 다 돌려 봐야 했다.
  2. **합창곡에서 음질이 크게 손상되고 악기 소리가 지워진다(spectral hole). 그 구간은 음량 자체가 작아져서 미디 프로그램으로 다시 키워야 했다.**
  3. 가끔 MR에 보컬이 섞여 나온다.
- MR 툴은 이미 많다. 그래서 **차별점이 첫 몇 초 안에 귀와 눈으로 확인돼야** 하고, 마케팅이 성패를 가른다. (사용자 판단)
- 이 프로젝트의 1차 목표는 기술 완성이 아니라 **실제 사용자로부터 첫 수익(1원)을 받는 것**이다.

### 성공 장면 (사용자가 정의)

동호회 단톡방에 이 툴로 만든 MR을 올렸을 때 "이거 어디서 만들었어?"라는 반응이 나오는 순간,
즉 **합창 부분에서도 반주가 원곡처럼 꽉 차게 들릴 때.**

## 3. 목표 / 비목표 / 반목표

### 목표 (v1)
- G1. 곡 하나 업로드 → 한 번 클릭 → 완성된 MR 다운로드. (Vocal Cut/Stem 두 번 돌릴 필요 없음)
- G2. 합창 구간의 반주 손실·음량 저하를 자동으로 복구한다. **이것이 핵심 차별점이다.**
- G3. MR에 남은 보컬 찌꺼기를 찾아내 줄이고, 어느 구간에 남았는지 보여준다.
- G4. 결과 화면에서 "일반 분리 vs 복구본"을 바로 A/B로 들어보고 비교할 수 있다. (제품 안에 마케팅 장치를 넣는다)
- G5. 결제는 MVP 이후(Phase 1.5)에 붙인다. 사업자등록이 없으므로 MVP는 무료 한도만 두고, 결제를 나중에 붙일 수 있게 크레딧 구조만 미리 만들어 둔다. (사용자 결정)

### 비목표 (v1에서 안 함, 나중에)
- 4-stem/다중 악기 분리(Stem 기능). 사용자가 "나중에 필요"라고 했다. v2 후보.
- 악기 판별 + 음색 학습 후 재합성(DDSP, 노트 전사 기반 복원). 장기 R&D 과제로 남긴다.
- 자체 분리 모델 학습. v1은 공개된 사전학습 모델만 쓴다.
- 모바일 앱, 실시간 처리, 팀/협업 기능.

### 반목표 (기술적으로 돌아가도 이렇게 되면 실패)
- A1. **원곡에 없던 소리를 지어내는 복구.** 복구는 반드시 원곡 믹스 안에 있는 정보를 근거로 한다. 생성 AI로 그럴듯하게 채우지 않는다.
- A2. 반주를 꽉 채우려다 합창(보컬)이 MR에 다시 새어 들어오는 것. "꽉 찬 반주"와 "보컬 없음" 사이의 균형이 핵심 튜닝 대상이다.
- A3. 엔진을 완벽하게 만들려다 웹 출시가 밀리는 것. 엔진 단계는 기간을 정해 두고(§7) 끝낸다.
- A4. 결제를 붙인 뒤(Phase 1.5) 유료 경로를 한 번도 실제로 결제해 보지 않고 "완료"라고 하는 것.

## 4. 제약

- 예산 최소. 개발 단계 GPU 비용은 0원이어야 한다. 로컬 PC에 **RTX 3060 12GB**가 있다.
- 사용자가 이전 프로젝트에서 쓴 도구를 재사용한다 (github.com/MS-Won의 Balance, Fit_Photo, Shorts, Monkey):
  - 웹: Next.js + React 19 + TypeScript + Tailwind v4 + Vitest, Vercel 배포
  - DB·인증·스토리지: Supabase
  - 처리 엔진: Python + pytest
  - 작업 방식: spec → plan → subagent-driven-development, `CLAUDE.md` + `docs/STATE.md` + `todo.md`로 여러 PC에서 이어서 작업, 커밋 메시지는 한국어로 이유를 남긴다.
- 새로 추가되는 인프라는 **서버리스 GPU(처리 시간만큼만 과금)** 하나뿐이다.
- 저작권: 사용자가 올린 곡과 결과물은 처리 후 일정 시간(기본 24시간) 뒤 자동 삭제한다. 공유·공개 기능은 만들지 않는다. 약관에 "본인이 사용 권한을 가진 음원만 업로드"를 명시한다.

## 5. 처리 엔진 설계 (Python)

엔진은 웹과 독립된 Python 패키지로 만든다. CLI로 로컬에서 돌릴 수 있어야 하고, 그대로 GPU 워커에 올린다.

```
입력 음원
  → [1] 디코딩·정규화 (44.1kHz. 모노 입력도 받는다 — 테스트 곡 중 1곡이 모노이며, 출력 채널 수는 입력을 따른다)
  → [2] 분리 앙상블 → 기본 MR + 보컬 추정치
  → [3] 합창 구간 검출
  → [4] 합창 구간 반주 복구 (spectral hole 채우기)
  → [5] 구간별 음량 복구
  → [6] 잔여 보컬 스캔·감쇄
  → 출력: MR(WAV/MP3) + 비교용 기본 MR + 분석 리포트(JSON)
```

### [2] 분리 앙상블 — 사용자 문제 1 해결
- 성격이 다른 공개 모델을 2개 이상 돌려서 주파수 단위로 합친다.
  - 예: RoFormer 계열(BS-RoFormer / Mel-RoFormer) 보컬·반주 모델 + HTDemucs 계열 4-stem 모델의 비보컬 스템 합.
  - 모델 로딩·실행은 UVR 모델을 감싼 오픈소스 패키지(`audio-separator` 등)를 우선 검토한다.
- 합치는 방식(평균, 주파수별 최소/최대값 등)은 빌더가 실험으로 정한다.
- 어떤 모델을 쓸지는 **§7 Phase 0의 청취 테스트 결과로 결정**한다. 라이선스가 상업적 이용을 허용하는지 반드시 확인한다.

### [3] 합창 구간 검출
- 보컬 추정치의 에너지, 대역 폭(합창은 리드 보컬보다 넓은 대역에 퍼짐), 원곡 대비 반주 에너지 감소량으로 "합창/보컬 집중 구간"을 찾는다.
- 결과는 시간 구간 목록이며, 리포트와 UI(파형 위 표시)에 쓰인다.

### [4] 합창 구간 반주 복구 — 핵심 차별점 (사용자 문제 2)
- 원인: 분리 모델이 넓게 퍼진 합창을 통째로 보컬로 보고, 같은 대역의 악기까지 같이 지운다.
- 원칙: 지워진 악기 성분은 **원곡 믹스에 아직 남아 있다.** 복구는 원곡 믹스(또는 원곡 − 보컬 추정치)에서 가져온다. (A1 준수)
- 접근 방향 (빌더가 실험으로 확정):
  - 합창 구간에서만 분리 마스크를 덜 공격적으로 완화하되, 대역별로 상한을 둔다.
  - 같은 곡 안의 합창이 없는 구간에서 측정한 반주의 대역별 에너지 분포를 "이 곡의 반주가 원래 어떻게 들려야 하는가"의 기준으로 삼고, 합창 구간에서 그 기준보다 많이 비어버린 대역만 채운다.
- 이 단계에는 **"반주 충만도 ↔ 보컬 누설"을 조절하는 강도 파라미터**를 둔다. v1 UI에는 기본값 하나만 노출하거나 3단계(약/중/강) 정도로만 노출한다. (빌더 판단, 아래 §9)

### [5] 구간별 음량 복구 (사용자 문제 2의 음량 부분)
- 합창 구간에서 MR 음량이 떨어지는 것을, 앞뒤 구간과 원곡의 흐름에 맞춰 자동으로 보정한다. 사용자가 미디 프로그램에서 손으로 하던 작업의 자동화다.
- 게인은 상한을 둔다. 보컬 찌꺼기까지 같이 키우면 안 된다(A2).

### [6] 잔여 보컬 스캔·감쇄 (사용자 문제 3)
- 완성된 MR에 보컬 검출을 한 번 더 돌려, 보컬이 남은 시간 구간을 찾는다.
- 찾은 구간은 추가 감쇄 처리를 하고, 리포트에 "보컬 잔여 의심 구간"으로 기록해 UI에 표시한다.

### 출력
- `mr_restored` (최종본), `mr_baseline` (복구 전 앙상블 MR — A/B 비교용), `report.json` (합창 구간, 복구 구간, 잔여 보컬 구간, 처리 시간).

## 6. 웹 서비스 설계

### 사용자 흐름
1. 랜딩 페이지: 첫 화면에 **같은 합창곡의 "일반 MR vs 복구 MR" A/B 플레이어**를 둔다. 문구 예: "합창이 빠져도 반주는 그대로."
2. 로그인 (Supabase Auth. 카카오/구글 소셜 로그인 우선)
3. 업로드 → 처리 중 표시 → 결과 화면
4. 결과 화면: 파형 위에 합창 구간과 복구 구간을 표시, A/B 토글, 잔여 보컬 의심 구간 표시, 다운로드
5. 무료 한도를 다 쓰면 크레딧 구매로 안내

### 구성
- **Next.js (Vercel)**: 랜딩, 업로드, 결과 화면, 결제
- **Supabase**:
  - Auth
  - DB: `profiles`(크레딧 잔액), `jobs`(상태, 입력/출력 경로, 리포트, 생성 시각), `credit_ledger`(충전·차감 원장)
  - Storage: 업로드 원본과 결과물. 24시간 뒤 자동 삭제.
  - RLS로 본인 작업만 보이게 한다. RLS 검증 스크립트는 anon 권한으로 돌려야 한다 (Balance 프로젝트의 교훈: `supabase db query --linked`는 슈퍼유저라 RLS를 우회함).
- **GPU 워커**: (2026-11-26 변경, 대표 결정) MVP는 **대표 PC(RTX 3060)를 워커로** 쓴다. 비용 0원, PC가 켜져 있을 때 한 번에 한 곡씩 처리. 사용자가 늘면 아래 서버리스 GPU로 옮긴다. 운영 체계 설계 `2026-11-26-ms-audio-org-design.md` §8 참고.
- (이전 계획, 이전 시 사용) **서버리스 GPU**: §5 엔진을 컨테이너로 올린다. 작업 요청 → 처리 → Storage 업로드 → `jobs` 상태 갱신.
  - 후보는 Modal, RunPod Serverless 등. 실제 곡당 비용을 측정해서 고른다.
  - **외부 API 형태는 계획서를 믿지 말고 라이브 문서로 확인한다** (Shorts 프로젝트의 교훈).

### 가격·결제
- MVP: 무료 한도만 둔다 (가입 시 2곡, 내 판단). `credit_ledger`로 차감만 기록해 두어 결제를 나중에 바로 붙일 수 있게 한다.
- 결제는 MVP 이후 Phase 1.5에서 붙인다 (사용자 결정). 사업자등록이 없으므로 그때 사업자등록 후 국내 PG를 쓸지, 개인이 받을 수 있는 수단을 쓸지 정한다.
- 가격: 크레딧 팩 (예: 5곡 / 20곡). GPU 실측 비용을 보고 정한다.

## 7. 진행 단계와 기간

완벽주의와 흥미 상실을 막기 위해 **각 단계에 기간 상한과 통과 기준**을 둔다.

### Phase 0 — 엔진 검증 (로컬, 최대 1주)
- 테스트 세트: 사용자가 `Test AR/`에 넣은 3곡 (git에는 올리지 않는다).
  - `#13 Do You Hear the People Sing.mp3` (약 3:20, **모노**, 192kbps) — 대규모 합창
  - `14. 낡은 침대를 타고.mp3` (약 4:34, 스테레오, 256kbps)
  - `14. 소리도둑 유봉 AR.mp3` (약 4:29, 스테레오, 320kbps)
- 로컬 RTX 3060에서 [2]~[6]을 돌리고, 같은 곡을 Gaudio로 돌린 결과와 비교한다. Gaudio 결과물은 사용자가 직접 만들어 `Test AR/gaudio/`에 넣는다.
- **통과 기준: 사용자가 들었을 때 합창 구간 반주가 Gaudio보다 확실히 더 꽉 차게 들린다.**
  - 통과 → Phase 1
  - 미달 → 기간 안에 원인을 정리해서 사용자와 방향을 다시 정한다. 기간을 넘겨 계속 다듬지 않는다(A3).

### Phase 1 — 웹 MVP (최대 2주)
- 업로드 → 처리 → 결과 A/B → 다운로드까지 끝에서 끝까지 동작 (무료 한도 적용).
- 배포된 URL에서 실제 곡 1개를 처음부터 끝까지 처리해 보고 나서 완료로 친다.

### Phase 1.5 — 결제
- 결제 수단을 정하고 크레딧 구매를 붙인다. **실제 결제를 1회 이상 해 보고 나서** 완료로 친다(A4).
- Phase 2 마케팅과 병행할 수 있다. 무료 사용자 반응을 먼저 보고 가격을 정하는 데도 쓴다.

### Phase 2 — 출시와 마케팅 (Phase 1 직후 시작)
- 1순위 채널: 사용자가 속한 **뮤지컬 동호회**. 직접 만든 MR을 공유해 "어디서 만들었어?" 반응을 유도한다.
- 2순위: 합창단·성가대·뮤지컬 커뮤니티(네이버 카페, 갤러리 등), 성악·뮤지컬 입시생.
- 콘텐츠: 같은 합창 구간의 A/B 비교 영상(15~30초). 사용자의 Shorts 파이프라인 경험을 재활용할 수 있다.
- 측정: 방문 → 가입 → 무료 사용 → 첫 결제 전환. 유입 경로를 source 파라미터로 추적한다.

## 8. 검증 방법

- 엔진: pytest 단위 테스트(입출력 형식, 길이 보존, 클리핑 없음, 구간 검출 동작) + **Phase 0 청취 테스트가 최종 판정**이다. 수치 지표는 참고용이다.
- 웹: Vitest. 돈이 오가는 경로(결제, 크레딧 차감)는 모킹 테스트만으로 완료 처리하지 않고 실제로 한 번 돌린다.
- RLS: anon 권한으로 다른 사용자 작업에 접근이 안 되는지 확인한다.

## 9. 빌더에게 맡기는 것 (내 판단으로 정한 것 포함)

- 앙상블에 쓸 구체적 모델과 합치는 방식 → Phase 0 실험으로 결정
- 합창 검출·복구 알고리즘의 세부 수식과 파라미터
